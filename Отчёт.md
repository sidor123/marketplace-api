# Отчёт: клиент-серверное приложение "Маркет"

## 1. Доменная область

"Маркет" - небольшой маркетплейс. Продавцы добавляют товары в каталог, указывают цену и количество на складе, меняют описание и снимают товары с продажи. Покупатели просматривают каталог. Через API также можно создавать, изменять и отменять заказы, применять промокоды.

За основу взят существующий проект marketplace-api. В нём уже были API, авторизация, товары, заказы и SQL-миграции. Для этого задания добавлены веб-интерфейс и настройки, необходимые для работы по методологии 12 факторов.

В интерфейсе доступны все CRUD-операции с товарами: создание, просмотр, изменение и удаление в архив. Продавец может менять только свои товары, администратор - любые. При регистрации можно выбрать роль покупателя или продавца. Аккаунт администратора создаётся отдельной командой.

## 2. Стек реализации

| Часть приложения | Технологии |
| --- | --- |
| Фронтенд | HTML, CSS и JavaScript без фреймворков. Запросы к серверу отправляются через `fetch` |
| Бэкенд | Python, Flask и Gunicorn. Обмен данными через HTTP/REST в формате JSON |
| Проверка входных данных | Pydantic. API описан в OpenAPI, модели для проверки данных создаются с помощью Datamodel code generator |
| Работа с БД | SQLAlchemy и psycopg |
| База данных | PostgreSQL |
| Авторизация | bcrypt для паролей и PyJWT для jwt-токенов |
| Сборка и запуск | Docker, Docker Compose |
| Миграции | SQL-файлы и миграции Python |
| Тесты | Python unittest и отдельная тестовая PostgreSQL |

Стек выбран достаточно простым: для работы нужны только приложение и PostgreSQL. Отдельный сервер для фронтенда не требуется, поскольку HTML, CSS и JavaScript отдаёт Flask. По умолчанию Gunicorn запускает два процесса. Для небольшого стенда можно оставить один, задав `WEB_CONCURRENCY=1`.

## 3. Основные сущности

| Сущность и таблица | Что хранит |
| --- | --- |
| Пользователь, `users` | ID, уникальный email, хеш пароля, роль USER/SELLER/ADMIN, даты создания и обновления |
| Товар, `products` | Название, описание, цену, остаток, категорию, продавца и статус ACTIVE/INACTIVE/ARCHIVED |
| Заказ, `orders` | Покупателя, статус заказа, итоговую сумму, скидку, промокод и даты |
| Позиция заказа, `order_items` | Товар, его количество и цену на момент покупки |
| Промокод, `promo_codes` | Код, размер и вид скидки, срок действия, минимальную сумму заказа и число использований |
| Операция пользователя, `user_operations` | Кто и когда создал или изменил заказ. Эти записи нужны для ограничения частоты таких действий |

У одного продавца может быть несколько товаров, а в одном заказе - несколько позиций. К заказу можно применить один промокод. Цена товара сохраняется в позиции заказа, поэтому последующее изменение цены в каталоге не меняет старые заказы.

При создании заказа количество доступного товара уменьшается, а при отмене возвращается обратно. Заказ и остатки сохраняются в одной транзакции: если возникает ошибка, изменения отменяются. Блокировки в PostgreSQL не позволяют двум покупателям одновременно купить последний экземпляр товара.

### CRUD товаров

| Действие | Запрос | Результат |
| --- | --- | --- |
| Создать | `POST /products` | Новый товар, 201 с его ID |
| Прочитать | `GET /products`, `GET /products/{id}` | Список товаров с фильтрами и разбивкой на страницы или один товар |
| Изменить | `PUT /products/{id}` | Обновлённые поля товара, 200 |
| Удалить | `DELETE /products/{id}` | Перевод в статус ARCHIVED, 204 |

Удаление здесь означает перенос в архив. Запись остаётся в базе, чтобы товар можно было посмотреть в старых заказах. Архивные товары доступны через фильтр статуса. При необходимости товар можно вернуть в продажу.

## 4. Как работает приложение

1. Браузер открывает `/` и получает страницу, JavaScript и CSS.
2. JavaScript отправляет запросы к API. Для действий, требующих входа, в заголовок `Authorization` добавляется JWT-токен.
3. Бэкенд проверяет токен и права пользователя. Например, продавец не может изменить чужой товар.
4. Pydantic проверяет данные запроса. При ошибке сервер возвращает JSON с пояснением и подходящим HTTP-кодом.
5. Код приложения обращается к PostgreSQL через SQLAlchemy. Успешные изменения сохраняются, а при ошибке транзакция откатывается.
6. Браузер получает ответ и обновляет страницу без полной перезагрузки. Введённые пользователем строки отображаются как текст, поэтому HTML-код из описания товара не выполняется.
7. Сервер записывает сведения о запросе в лог: ID, адрес, код ответа и время обработки. Пароли и токены туда не попадают.

Токены хранятся в памяти вкладки браузера. После перезагрузки страницы нужно войти заново. Серверу не нужно хранить сессию пользователя в памяти конкретного процесса.

## 5. Соответствие 12 факторам

Ниже описано, как в проекте выполняется каждый пункт 12 факторов. Отдельные рабочее и тестовое окружения на сервере не развёрнуты, но для них предусмотрен одинаковый способ сборки и запуска.

### 1. Кодовая база

Весь проект хранится в одном Git-репозитории: фронтенд, бэкенд, описание API, миграции и настройки сборки. Для разработки, тестового сервера и рабочего сервера используется один и тот же код. Различаются только настройки окружения.

При сборке можно передать номер коммита через `SOURCE_REVISION`. Он сохраняется в метаданных Docker-образа, чтобы было понятно, из какой версии кода собран образ.

**Файлы:** `Dockerfile`, `scripts/package.py` и структура репозитория.

### 2. Зависимости

Все Python-зависимости и их версии перечислены в `requirements.txt`. Там указаны и библиотеки, которые нужны другим библиотекам. Инструменты для сборки вынесены в `requirements-build.txt`. Фронтенд не загружает пакеты, шрифты или скрипты со сторонних сайтов.

Docker изолирует приложение от пакетов на компьютере, где оно запускается. Для запуска без Docker используется виртуальное окружение `venv`. Версии Python и PostgreSQL также указаны явно.

Модели из OpenAPI создаются при сборке. Готовый образ уже содержит нужные файлы и зависимости, поэтому при запуске ничего скачивать не нужно. Для повторного запуска конкретного релиза используется ID собранного образа. Полное совпадение результатов двух отдельных сборок не гарантируется: для этого потребовалось бы дополнительно закрепить базовые образы по их контрольным суммам.

**Файлы:** `requirements.txt`, `requirements-build.txt`, `Dockerfile`, `scripts/generate_schemas.sh`.

### 3. Конфигурация

Настройки, которые могут отличаться между окружениями, передаются через переменные среды. К ним относятся адрес и пароль БД, ключ JWT, порт, число процессов, размер пула соединений, сроки действия токенов и уровень логирования.

Без `DATABASE_URL` и  `JWT_SECRET_KEY` сервер не запустится. Рабочие пароли и ключи в коде не заданы. Для обычных настроек есть значения по умолчанию, например порт 8000.

В `.env.example` приведён пример конфигурации. Скрипт `scripts/init_env.py` создаёт локальный `.env` со случайными паролями. Существующий файл он не перезаписывает. Сам `.env` не попадает в Git, Docker-образ и архив. Compose читает его и передаёт значения приложению как переменные среды.

**Файлы:** `app/config.py`, `app/database.py`, `app/auth_service.py`, `gunicorn.conf.py`, `.env.example`.

### 4. Сторонние сервисы

PostgreSQL подключается через `DATABASE_URL`. Чтобы подключить другую PostgreSQL, достаточно изменить адрес и данные для входа.

В Compose данные БД хранятся в отдельном томе. Они не зависят от файловой системы контейнера приложения. Если нужно перенести уже накопленные данные в другую базу, это делается отдельно, например через резервную копию.

**Файлы:** `app/database.py`, `docker-compose.yml`.

### 5. Сборка, релиз, запуск

Эти три этапа разделены.

- **Сборка:** `docker compose build api` устанавливает зависимости, создаёт модели из OpenAPI и собирает образ с фронтендом и бэкендом. Подключение к БД и рабочие секреты не нужны.
- **Релиз:** `scripts/release.py` связывает ID готового образа с копией настроек и присваивает релизу `RELEASE_ID`. Создать второй релиз с тем же ID нельзя. Миграции выполняются отдельной командой из того же образа.
- **Запуск:** Compose запускает готовый релиз с флагом `--no-build`. Код с компьютера разработчика не подставляется в контейнер. При старте сервера не устанавливаются пакеты и не выполняются миграции.

Если меняется код или конфигурация, создаётся новый релиз. ID запущенного релиза можно узнать через `/health/live`. Файлы с настройками релизов содержат секреты, поэтому не включаются в исходники и архив. После выпуска их не следует редактировать.

Для запуска на другой машине нужно перенести тот же образ или загрузить его из хранилища образов по контрольной сумме. При возврате к старой версии приложения нужно учитывать совместимость со схемой БД: автоматический откат миграций не предусмотрен.

**Файлы:** `Dockerfile`, `scripts/release.py`, `docker-compose.yml`, `README.md`.

### 6. Процессы без состояния

Пользователи, товары, заказы, остатки и история операций хранятся в PostgreSQL. Приложение не сохраняет эти данные в памяти процесса или в локальных файлах. Для проверки JWT все копии приложения используют один ключ.

Поэтому сервер можно перезапустить или запустить на другой машине, подключив его к той же БД. Сохранённые данные останутся на месте. Если процесс завершится посреди операции, PostgreSQL отменит незавершённую транзакцию.

**Файлы:** `app/database.py`, `app/auth_service.py`, `app/order_service.py`, том `postgres_data` в Compose.

### 7. Привязка портов

HTTP-сервер Gunicorn входит в зависимости приложения и сам принимает запросы. Он слушает адрес `0.0.0.0` и порт из переменной `PORT` - через него доступны интерфейс, API и проверки состояния сервера.

В Compose внешний порт задаётся отдельно через `HOST_PORT`, для запуска не требуется дополнительный веб-сервер.

**Файлы:** `gunicorn.conf.py`, `Dockerfile`, `docker-compose.yml`.

### 8. Параллелизм

Количество процессов Gunicorn задаётся через `WEB_CONCURRENCY`. Если нужно запустить несколько копий приложения, можно увеличить число контейнеров `api`.

В README приведён пример запуска трёх копий с отдельными свободными портами. Все они работают с одной PostgreSQL. Блокировки в БД помогают правильно обрабатывать одновременные заказы. Отдельный тест проверяет, что два покупателя не могут купить один и тот же последний товар.

Миграции и создание администратора запускаются отдельными процессами.

**Файлы:** `gunicorn.conf.py`, `docker-compose.yml`, `app/order_service.py`, `tests/test_app.py`.

### 9. Быстрый старт и корректное завершение

Сервер запускается из готового образа, поэтому ему не нужно устанавливать зависимости или менять схему БД при каждом старте.

При получении SIGTERM Gunicorn перестаёт принимать новые запросы и даёт текущим завершиться. На это отведено 25 секунд, а Compose ждёт 30 секунд перед принудительной остановкой контейнера. Настройка `init: true` помогает передавать сигналы и завершать дочерние процессы.

Для подключения к БД и выполнения SQL заданы ограничения по времени. Пул соединений проверяет, доступна ли база после её перезапуска. `/health/live` отвечает, работает ли сервер, а `/health/ready` проверяет доступ к таблице товаров.

При падении приложения сохранённые данные остаются в PostgreSQL - поддерживается at-least-once доставка.

**Файлы:** `gunicorn.conf.py`, `docker-compose.yml`, `app/database.py`, `app/main.py`.

### 10. Сходство окружений

Для разработки и запуска на сервере предусмотрены один Dockerfile, одинаковые версии Python, Gunicorn и PostgreSQL. В тестах также используется PostgreSQL. Между окружениями меняются настройки и адреса сервисов, но не код приложения.

Команды сборки, выпуска релиза и запуска описаны в README и Makefile. Их можно использовать для автоматического развёртывания.

**Файлы:** `Dockerfile`, `docker-compose.yml`, `Makefile`, `README.md`.

### 11. Логирование

После каждого HTTP-запроса приложение пишет в stdout строку JSON. В ней есть время, ID запроса, метод, путь, код ответа, длительность и ID пользователя, если он вошёл в систему. ID запроса также возвращается клиенту в заголовке `X-Request-Id`.

Тела запросов, пароли и токены в логи не записываются. Gunicorn выводит свои сообщения и ошибки в stderr. Приложение не создаёт файлы логов и не занимается их хранением или очисткой. Логи можно смотреть через `docker compose logs`, а при необходимости собирать внешними инструментами.

**Файлы:** `app/logging_middleware.py`, `gunicorn.conf.py`, тесты логирования в `tests/test_app.py`.

### 12. Административные задачи

Миграции запускаются командой `python -m app.migrate` отдельно от сервера. Для них используется тот же Docker-образ, те же зависимости и тот же `DATABASE_URL`.

В таблице `app_schema_migrations` сохраняются версии и контрольные суммы выполненных SQL-файлов. Если уже выполненную миграцию изменили, команда сообщит об ошибке. Блокировка в PostgreSQL не позволяет двум процессам одновременно применять миграции. Изменения выполняются в одной транзакции, а повторный запуск не выполняет их заново.

Администратор создаётся командой `python -m app.admin`. Она также запускается из образа приложения и получает email и пароль через переменные среды. Ни миграции, ни создание администратора не выполняются автоматически при старте каждого процесса сервера.

**Файлы:** `app/migrate.py`, `app/admin.py`, `db/migration/`, сервис `migrate` в Compose.

## 6. Запуск и состав архива

Все команды приведены в [README.md](README.md). Порядок запуска: подготовить настройки, собрать образ, создать релиз, запустить PostgreSQL, выполнить миграции и запустить приложение. После этого интерфейс доступен по адресу `http://localhost:8000`.

Команда `python3 scripts/package.py` создаёт архив `artifacts/marketplace-homework.zip`. В нём находятся исходники фронтенда и бэкенда, описание API, SQL-миграции, списки зависимостей, Dockerfile, Compose, тесты, инструкция запуска и этот отчёт.

Пароли, локальные окружения, кэш и служебные файлы Git в архив не попадают. Файлы моделей, которые создаются из OpenAPI, будут получены при сборке.

## 7. Проверка результата

Пройдены 11 тестов на PostgreSQL, включая CRUD, права доступа, одновременную покупку последнего товара, завершение сервера по SIGTERM и чтение данных после перезапуска.
